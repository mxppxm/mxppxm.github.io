**TL;DR**

- **彩度峰值不在中间档。** Tailwind 的蓝在 `blue-600` 才到顶（0.245），比 `blue-500` 高 14.5%；绿色更反常，峰值在 `emerald-400`。
- **两端必须收。** 最浅一档只留峰值的 5.7–11.9%，最深一档留 28.8–37.1% —— 收了才不发灰、不发脏。
- **色相跟着明度漂。** 橙从 73.7° 走到 36.3°（往红里靠），蓝只走 13.3°，绿只走 6.4°。暖色漂得多，冷色漂得少。

## 01 · 一条色阶里其实有三个变量，大多数人只动了其中一个

`hsl()` 的 L 骗了很多人：同样写 50%，黄在屏幕上跳出来、蓝沉下去 —— 因为 HSL 的 L 只是「混了多少白、多少黑」的算术平均，**不是眼睛看到的分量**。2020 年 Björn Ottosson 发布的 OKLab 就是修这个病的，几年后它进了 CSS Color 4，`oklch()` 现在在 Chrome 111、Safari 15.4、Firefox 113 之后都能直接写。

OKLCH 把颜色拆成三个真正正交的旋钮：**L** 感知亮度、**C** 彩度（灰 → 最艳）、**H** 色相角。正交的意思是，拧 L 的时候 C 和 H 不会乱跑 —— 于是做色阶从「调一个数」变成「同时决定三件事」。而大多数人只做了第一件：L 一路下压，C 和 H 死死不动。结果不是色阶，是一条**饱和度渐变的灰带**。

公开教材就摆在 **Tailwind v4** 的 `theme.css` 里：26 个色相 × 11 档，全部用 `oklch()` 写，值谁都能下载。把蓝色那一列摊开看，三个变量同时在动：

| 档位 | L | C | H |
| --- | --- | --- | --- |
| blue-50 | 97% | 0.014 | 254.6 |
| blue-300 | 80.9% | 0.105 | 251.8 |
| blue-400 | 70.7% | 0.165 | 254.6 |
| blue-500 | 62.3% | 0.214 | 259.8 |
| blue-600 | 54.6% | 0.245 | 262.9 |
| blue-800 | 42.4% | 0.199 | 265.6 |
| blue-950 | 28.2% | 0.091 | 267.9 |

**第一，L 不是等距的。** 97% 到 28.2% 之间 9 档的间隔在 4–10 点之间浮动，越往暗处越密 —— 暗端做成等距，肉眼就会觉得后几档糊成一团。

**第二，C 是钟形，峰值位置还因色相而异。** 蓝的峰值在 600（0.245），压过了「中间档」500（0.214）；橙也在 600；绿却在 400（0.177）就到顶。**第三，H 会漂，暖色漂得最凶：** 橙从 73.7° 一路走到 36.3°，整整 **37.4°** —— 73° 的暗橙会读成土黄，只有往 30–40° 靠，它在深色背景上才还是「橙」。绿只漂 6.4°，它不需要逃。

可以直接抄的三步：

1. **L 定架子：** 97 / 93 / 88 / 81 / 71 / 62 / 55 / 48 / 42 / 38 / 28，暗端加密。
2. **C 走钟形：** 峰值放在 L ≈ 62%，最浅端收到峰值的 6%，最深端收到 35%。
3. **H 往暗处漂：** 暖色往红移 20–40°，冷色往紫移 6–15°，绿基本不动。

验收只有一条：转成灰度看，相邻两档差 6–9 个 L 点。出现 3 点的相邻档，它们在 UI 里一定打架。

## 02 · 作品 pick：一个只换明度，一个把色阶改成用途

### ① Vercel 的 Geist —— 一个 token 供两套主题

Vercel 首页的产物 CSS 里有一段写法值得直接抄：`oklch(from var(--ds-gray-200) 0.94 c h)`，暗色主题那行是 `oklch(from var(--ds-gray-200) 0.27 c h)`。这是 CSS 的**相对颜色语法**：`from` 后面给一个源色，然后只覆写你想改的那一个分量 —— 这里的 `c` 和 `h` 原样继承源色，只有 L 被换成 0.94 或 0.27。

好处不只是省字符。你的灰阶从此只需要维护一次：新增一个灰色 token，两套主题自动都有对应值，而且**色相永远一致** —— 不会出现亮色模式偏蓝、暗色模式偏紫那种「两套主题像两个产品」的毛病。这正好是第 01 章那条规则的工程实现：L 是变量，C 和 H 是常量。

**你能偷什么：** 把「亮/暗各一套色值」改成「一套色值 + 两行相对颜色」。L 用 0.94 / 0.62 / 0.27 三档就够撑起背景层、边框层、文本层。改品牌色时只改源 token，两套主题跟着走。注意兼容性：相对颜色语法 Chrome 119、Safari 16.4、Firefox 128 起支持，旧浏览器得留 fallback。

### ② Radix Colors —— 把色阶从「明度阶」改成「用途阶」

Radix 的 12 个 step 不是 12 个亮度，是 **12 个用途**：1 应用背景、2 次级背景、3–5 组件背景（常态/悬停/按下）、6–8 边框（低调/常态/强调）、9–10 实心填充（常态/悬停）、11–12 文本。文档里明说，11 和 12 这两步是为文本设计的、对比度是有保证的。

这是个思路上的转向：色板不按「多深」组织，按「它要干什么」组织。换主题时你不用再想「这个灰该用 200 还是 300」，只需要问「这是背景还是文本」。这也解释了为什么 Radix 的每档彩度都是手工微调的 —— 每一档的 KPI 不同，第 3 档要和背景拉开，第 9 档要能扛住白字。

**你能偷什么：** 把你的 11 档色板重新命名成 `bg / bg-subtle / surface / border / solid / text` 这套语义，档位数一个不用动。名字一改，团队里「这个灰到底用哪一档」的争论会消失一半。

## 03 · 两个能立刻用的工具

### ① oklch.com —— Evil Martians 的三滑杆取色器

Andrey Sitnik 与 Roman Shamin 做的，三根滑杆分别拧 L / C / H，实时给出 sRGB fallback、3D 色域视图，还能直接切到 **APCA** 算对比度。APCA 是 WCAG 3 草案里的新对比度算法，按感知对比算，比 WCAG 2 那个一刀切的 4.5:1 更接近「你到底能不能读清」。做深色主题时用它，你会发现自己有一半的「合格」配色其实是灰字压灰底。

### ② Tailwind v4 的 theme.css —— 286 个调好的 oklch 值

26 × 11，公开、可直接抄进你的 `@theme`。但请**抄数，别抄公式**：它的峰值位置是逐色手调的，不存在一个能套所有色相的公式。你要换成自己的品牌色相，还得把第 01 章那三个决定重新走一遍 —— 这也正是这期想说的：色阶是设计出来的，不是算出来的。

## 🎯 今天动手：把最深那档的彩度砍到 35%

1. **打开 oklch.com，填你项目里的品牌色** —— 记下它的 H，从现在开始锁死不动。
2. **只拉 L，做 5 档** —— 97 / 84 / 70 / 52 / 32，中间那三档的 C 先保持原样。
3. **把最深那档的 C 手动砍到中间档的 35%** —— 然后把两个版本并排贴在同一个深色背景上。砍过的那档会立刻「立」起来，没砍的那档像蒙了层灰。
4. **顺手验收** —— 把 5 档转灰度，看相邻两档的 L 差是不是都在 6–9 点之间。不够就挪，别加档。
